Social analytics — research: what each platform lets us pull#

Date: 2026-11-04 · Status: RESEARCH (no code yet) · Next step: a design/plan doc for the build.

Goal: pull view + engagement analytics from every connected social account into the CMS, store them, show a cross-platform dashboard, and later let AI summarise and analyse them — our own build, informed by what Hootsuite / Sprout Social & co. do.

Sources are official developer docs unless noted; items the research could not confirm are marked (unverified) — check them against a live account before building on them.

Three facts shape the whole design:

  1. No platform keeps long history for us. Follower counts are "now" values almost everywhere (IG ≤ 30 days of deltas, TikTok 60 days, X none, Patreon none). Every competitor's #1 documented limitation is "data starts the day you connected". → Snapshot every account and every post DAILY from day one, into our own tables. Start this before building any UI.
  2. Some data is only catchable while it's fresh: Instagram Stories (24 h), X non-public metrics (posts < 30 days), YouTube Reporting API files (downloadable 60 days), TikTok profile metrics (60 days). The collectors must run on schedule, not on demand.
  3. "Views" is not one unit. Meta replaced impressions/plays with views (2025), YouTube changed how a view counts twice (Shorts 2025, all formats Aug 2026), X counts impressions, TikTok counts plays. Store raw platform metrics; derive one normalised "Views" figure with a per-platform mapping and mark the dates where a platform changed its definition.

3. Per platform#

3.1 YouTube — the best API#

What we have today: Data API v3 (API key, public data) + "Sign in with Google" with youtube.readonly and a refresh token (services/oauth/google.ts, social/youtubeAuth.ts).

Three APIs, use all three:

API Gives Shape Latency / history Quota
Data API v3 (channels.list, videos.list part=statistics) subscriberCount (rounded), channel viewCount, videoCount; per video views, likes, comments (dislikes owner-only) current values only near real-time; no history 10,000 units/day, 1 unit per call (50 videos per call)
Analytics API v2 (reports.query, ids=channel==MINE) views, engagedViews, estimatedMinutesWatched, averageViewDuration, averageViewPercentage, likes, dislikes, comments, shares, subscribersGained/Lost, playlist adds, card clicks, retention curves, live concurrents; dimensions day / video / country / traffic source / device / age / gender / content type (VIDEO / SHORTS / LIVE) per day, per video ~48–72 h lag; history back to channel start per-query cost (numbers unverified) — a daily pull is small
Reporting API v1 (bulk jobs) daily CSV files for every report type, incl. the reach reports (Jan 2026): video_thumbnail_impressions, video_thumbnail_impressions_ctr one file per day ~2 days; backfills 30 days before the job; files kept 60 days — download them negligible

Requirements

  • Add scope yt-analytics.readonly (keep youtube.readonly; Google now lists it as required for reports.query too). The channel owner re-consents once (incremental authorization). Revenue needs yt-analytics-monetary.readonly and a YouTube Partner Program channel — skip unless wanted.
  • The signer must be the channel owner (for a Brand Account, pick the brand channel at consent). Managers without owner rights get nothing.
  • Google Cloud OAuth consent screen must be "In production" — in "Testing" refresh tokens die after 7 days. For our single-owner use the app can stay unverified (an "unverified app" warning at consent, ≤ 100 users); sensitive-scope verification is only needed for wider use.

Not available / caveats

  • No real-time analytics (use Data API snapshots for "live" counters).
  • Subscriber count is rounded (3 significant figures) and hidden if the owner hides it.
  • View definitions changed: Shorts views count every start/replay since 2025-03-31, and from 2026-08-24 views count from the first frame for all formats — engagedViews keeps the old meaning. Show both, and annotate the change dates on charts.
  • Community posts: no analytics found. Traffic-detail rows capped at top 25.
  • Workarounds: YouTube Studio CSV export (manual upload) for anything missing; scraping Studio is against the ToS — don't.

3.2 Instagram (Business / Creator accounts)#

What we have today: graph.facebook.com/v21.0/{ig-user-id}/media with like_count, comments_count and a long-lived token. Move to a current Graph version — views doesn't exist in older ones.

Endpoints

  • Account: GET /{ig-user-id}/insights — reach, views (replaced impressions, removed 2025-04-21), likes, comments, shares, saves, reposts, total_interactions, accounts_engaged, follows_and_unfollows, follower_count (daily delta), profile_links_taps, follower_demographics, engaged_audience_demographics, online_followers. Plus followers_count on the user node (snapshot).
  • Per media GET /{ig-media-id}/insights:
    • Feed: views, reach, likes, comments, shares, saved, total_interactions, follows, profile_visits, profile_activity, reposts.
    • Reels: the above + ig_reels_avg_watch_time, ig_reels_video_view_total_time, reels_skip_rate, crossposted_views, facebook_views.
    • Stories: views, reach, replies, shares, follows, profile_visits, link_clicks, navigation — only for 24 hours.

Requirements

  • The account must be Business or Creator (a free switch in the app). Personal accounts get nothing.
  • Use "Instagram API with Instagram Login" (no Facebook Page needed; graph.instagram.com): permissions instagram_business_basic + instagram_business_manage_insights. (The Facebook Login path needs the account linked to a Page + instagram_manage_insights, pages_read_engagement.)
  • Standard Access is enough for accounts we own and add to our own Meta app (app role / Instagram Tester) — no App Review or Business Verification needed for that. Advanced Access and review only matter if other people's accounts connect.
  • Long-lived token = 60 days; refresh with refresh_access_token once it is ≥ 24 h old and before it lapses (a lapsed token can't be refreshed) → schedule at ~day 50.
  • Rate limits: Business Use Case limits, far above a daily batch. Free.

Not available / caveats

  • Follower history: at most ~30 days of daily deltas (unverified exact window) → snapshot daily.
  • Under 100 followers: no demographics, follower deltas or online-followers.
  • Stories: capture within 24 h — subscribe to the story_insights webhook or poll every few hours while a story is live. Story metrics under 5 return an error.
  • Watch time exists for Reels only. Carousel children have no insights.
  • Data can lag up to 48 h. Metric names change (impressions → views); handle "invalid metric" per metric, never fail the whole pull.
  • Backfill: Meta Business Suite CSV export (manual) for history before we started.

3.4 Threads (not a provider yet — cheap to add)#

/{threads-media-id}/insights: views, likes, replies, reposts, quotes, shares; /{threads-user-id}/threads_insights: views (time series), likes, replies, reposts, quotes, clicks, followers_count, follower_demographics (≥ 100 followers). 3.6 X (Twitter)#

What we have today: manual paste-by-URL with free syndication hydration (public like/reply counts only); a working OAuth 1.0a user-context signer; paid read-sync opt-in.

Pricing (since 2026-02-06): pay-per-use credits, no subscription, spend cap per cycle. Post read $0.005; "owned reads" $0.001 (reading your own account's data with an app owned by that same account); user read 0.010; same − dayre − readsbilledonce; cap3Mpostreads/month. * *Ourcost: 5/month** reading our own ~150 recent posts daily at owned-read rates (~$25 at standard rates). The old Free/Basic/Pro tiers are gone or migrating.

Stat Field

Video views media public_metrics.view_count

3.7 Patreon#

API v2 (OAuth, creator token): campaign patron_count; members with patron_status, currently_entitled_amount_cents, campaign_lifetime_support_cents, pledge history; posts (title, is_paid, published_at, tiers) — no views, likes or comments on posts. Webhooks: members:create|update|delete, members:pledge:*, posts:publish|update|delete (HMAC-MD5 signature). Rate limits 100 req / 2 s per client and 100 / min per token; send a User-Agent. Free.

Not available: post engagement, an earnings-over-time endpoint, patron-count history, the dashboard's "followers". → Snapshot patron_count + summed entitled amounts daily; count gained/lost from members:* webhooks; monthly income = sum of entitled amounts (an approximation — declines and refunds show only through last_charge_status). Creator dashboard CSV exports for history (columns unverified). The unofficial v1 internal API exposes post like/comment counts but is undocumented and against the spirit of the ToS — not recommended.

4. Data we can't get — why, and the options#

Gap Why Recommended "Hackish" option (not recommended)
History before we connect (all) Platforms only expose recent windows or current counts Start daily snapshots now; one-time manual CSV import per platform (YouTube Studio, Meta Business Suite, TikTok Studio, X analytics, Patreon) into the same tables —
Instagram Stories after 24 h Insights vanish with the story story_insights webhook + poll every 2–4 h while live —
X non-public metrics after 30 days API restriction daily pull keeps the last value before day 30 —
TikTok watch time on a personal account Display API doesn't have it switch the account to Business (free) and use the Business API scraping — ToS violation
Patreon post views / likes not in API v2 treat Patreon as revenue + members, not reach internal v1 API / Apify scrapers — ToS risk, breaks without notice
X / IG profile views, X demographics not exposed manual CSV upload browser automation of the analytics UI — ToS risk, account-ban risk
Meta metric churn Meta deprecates metrics yearly per-metric adapter; store raw JSON; tolerate "invalid metric" —

A manual CSV import screen (per platform, mapped to our metric names) is the honest, low-risk answer for every hole — the competitors' "since connected" problem with an escape hatch. Scraping/browser-automating the official dashboards is technically possible (a headless browser logged in as the owner, reading Studio pages) but violates every platform's terms, breaks on UI changes, and risks the account itself — not worth it for an account we depend on.

5. Lessons from Hootsuite, Sprout Social, Buffer, Metricool, Agorapulse, Later#

  • Everyone's #1 documented limitation is "data starts when you connected" (Hootsuite, Sprout, Buffer, Metricool). Sprout backfills ~2 years of Instagram post metrics but not follower counts; X: 1 year of posts, no audience backfill; Stories: never. → Confirms §1 fact 1.
  • Shared structure: a cross-network overview (audience, views, engagements, net growth) → per-profile report → per-post performance table → exports. Copy it.
  • Engagement rate has no standard. Hootsuite offers three denominators (reach / followers / impressions-views); its own example shows 5.21 % vs 1.25 % for the same post. Sprout defaults to per-impression. → Let the user pick the basis; always show the formula in a tooltip.
  • Net follower growth = gained − lost. Where a platform only gives a count (TikTok, Facebook, Threads), Sprout labels it "change in followers" — do the same.
  • Meta's views change: Sprout folded IG views into its cross-network "impressions" slot and kept old impressions only for pre-2025 periods. We'll name the unit "Views" and annotate the switch date instead of pretending they're the same.
  • AI summaries exist everywhere now (Sprout Trellis, Buffer AI Takeaways, Agorapulse, Hootsuite insight cards) — short narrative per report. Cheap for us to add on top of stored data.
  • Best time to post should come from our own post history (Later's approach); vendors' generic "best times" contradict each other.
  • Exports: CSV (summary + posts + timeseries, Buffer-style), PDF, scheduled email report.
  • Competitor tracking (public stats of other accounts, from the day added) is a common paid feature — possible later via public endpoints (YouTube Data API on any channel; others limited).
  • Pitfalls they document: mixing denominators silently; summing "impressions" across networks as one unit; treating Stories/TikTok as backfillable; hard-coding one Meta metric name; relying on X (Metricool even caps X retention at 30 days).
  • Pricing context (unverified, per seat/month): Hootsuite $99–399, Sprout 79–399 + quote − onlyPremiumAnalytics; Bufferperchannel; Metricool 20+/5 brands. Their paywalls sit on custom reports, competitor tracking and scheduled exports — the parts worth building well.

6. Recommended design for our build (to turn into a plan)#

Principle: collectors write raw daily snapshots; everything you see is derived from our own tables. Platform APIs are only a source, never the store.

  1. Storage (new tables)
    • social_account_snapshots — (connection, date, followers, following, posts count, total likes/views when the platform gives them, raw JSON). One row per account per day.
    • social_account_daily — (connection, date, metric, value, dimension?) for platform daily series (YouTube views/watch time/subs gained, IG reach/views, FB page metrics, TikTok Business profile metrics). Re-written for the last N days each run (YouTube revises ~3 days).
    • social_post_metrics — (social_post_id, date, views, likes, comments, shares, saves, watch_time_s, avg_watch_s, completion_rate, reach, impressions, clicks, raw JSON) — a daily snapshot per post for its first ~90 days, then weekly (cheap, and gives "views at day 7" comparisons).
    • social_metric_definitions — our normalised metric keys ↔︎ each platform's raw name + the date ranges where a definition changed (Meta views 2025-04-21, YouTube views 2025-03-31 / 2026-08-24) → chart annotations.
    • Reuse social_posts (we already capture posts) and social_connections (tokens).
  2. Collectors — one per provider behind ONE interface (collectAccount, collectPosts, collectDaily, optional onWebhook), registered like the shop providers; a daily social-analytics cron (primary only) + a 3-hourly Instagram Stories sweep; per-metric error tolerance; token refresh jobs (IG ~day 50, Google refresh token, TikTok refresh).
    • YouTube: Data API snapshot + Analytics API (last 5 days, day×video) + Reporting API reach jobs.
    • Instagram: account insights + media insights (Feed/Reels/Stories) via Instagram Login.
    • Facebook: page insights + post insights.
    • TikTok: Display API now; Business API when approved.
    • X: owned reads (opt-in, spend-capped setting) — keep paste-by-URL as the free mode.
    • Patreon: daily campaign/member snapshot + members:* webhooks.
  3. Derived metrics (computed in SQL from the snapshots): net follower change, avg views/likes per post, engagement rate (user-selected basis), watch-time averages, growth over period, top posts, per-platform and all-platform totals — each with a definition tooltip.
  4. Dashboard (admin → Social → Analytics): cross-network overview → per-account tab → per-post table (sortable, filter by type: video / short / reel / story / post) → charts with "since connected" markers and definition-change annotations → CSV/PDF export → optional weekly email report (existing mail + notifications plumbing).
  5. AI layer (later): a weekly/monthly summary built from the derived tables (top posts, what changed, anomalies, best times from our own history), stored per period and shown on the dashboard; ad-hoc "ask about my analytics" over the same tables.
  6. Manual import: per-platform CSV upload mapped into the same tables, for history and gaps.
  7. Permissions: social.analytics:view (staff) / social.analytics:manage (admin: collectors, X spend cap, imports).

Phasing suggestion: (1) snapshot tables + YouTube + Instagram + Facebook collectors (all free, largest value) → (2) dashboard + derived metrics → (3) TikTok Display + Patreon → (4) X owned reads, TikTok Business, Threads → (5) AI summaries, exports, email report, CSV import.

7. Account setup checklist (what you'll need to do)#

  • YouTube: re-connect "Sign in with Google" once we add yt-analytics.readonly; make sure the Google Cloud OAuth consent screen is In production (else tokens die in 7 days); sign in with the account that owns the channel.
  • Instagram: confirm the account is Business or Creator; in our Meta app add the Instagram product with Instagram Login, add the account as a tester/app role, grant instagram_business_basic + instagram_business_manage_insights.
  • Facebook Page: Page token with read_insights, pages_read_engagement, pages_show_list; you need the Page's ANALYZE (or admin) role.
  • TikTok: create a TikTok developer app (Login Kit + Display API scopes user.info.basic, user.info.stats, video.list) and submit it for review; for watch time/demographics, switch the TikTok account to a Business Account and apply for TikTok for Business API access.
  • X: only if wanted — buy API credits in the X Developer Console with a monthly spend cap, from the same X account that will be read (owned-read pricing).
  • Patreon: register a v2 client with campaigns, campaigns.members, campaigns.posts, w:campaigns.webhook.
