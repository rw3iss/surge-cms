# SiteSurge CMS

## Project Overview

SiteSurge (a.k.a. SiteSurge CMS) is a self-hosted, feature-based, block-based general-purpose CMS. Pages, posts, campaigns, forms, users, media, social connections, plus a custom header/footer editor and a global appearance system (swatches, fonts, block-style templates).

Monorepo with five workspaces under `packages/*`: `api` (`@sitesurge/server`, Express/Node), `cms` (`@sitesurge/admin`, SolidJS), `shared` (`@sitesurge/types`, types/DTOs/utils consumed by all), `cms-client` (`@sitesurge/client`, headless TS client — **fully implemented**), `cms-mcp` (`@sitesurge/mcp`, MCP server wrapping the client — **implemented**; see `docs/MCP.md`). All build/tool config lives in `./config`.

**Stack:** SolidJS + Vite | Express + PostgreSQL + Redis | Stripe | Patreon OAuth | S3/Local storage

Packages are scoped **`@sitesurge/*`** (`@sitesurge/types` = shared, `@sitesurge/server` = api, `@sitesurge/admin` = cms/web, `@sitesurge/client`, `@sitesurge/mcp`). Note the **package directory names still lag the package names** — `@sitesurge/server` lives in `packages/api`, `@sitesurge/admin` in `packages/cms`, `@sitesurge/types` in `packages/shared` (pnpm resolves by name, not path). The local repo dir (`rw-cms`) is cosmetic; the GitHub repo is `surge-cms`.

**npm distribution:** all packages publish to npm under `@sitesurge/*` (GPL-2.0-only) — `types`, `client`, `mcp` (libs), plus `server` (backend; serves the admin), `admin` (built SPA static assets; `adminDistPath()` resolver, bundled/served by the server), `cli` (`sitesurge` ops CLI), and `create-sitesurge` (`npm create sitesurge`, `--node` scaffolds a thin npm-server repo). `server`/`admin`/`cli` are a Changesets **fixed group**. The server also ships as a Docker image at `ghcr.io/rw3iss/sitesurge-server`. Consumers run the CMS without cloning: Docker image, or `@sitesurge/server` as an npm dep (`startServer()`/`createApp()`). The server's build copies `db/*.sql` into `dist` (see `packages/api/scripts/copy-assets.mjs`); fresh-install migrations are idempotent so a new DB migrates to a zero-drift schema. Design: `docs/superpowers/specs/2026-07-13-full-npm-distribution-design.md`.

## Core Capabilities
- **Block-based editor** — categorized AddBlockMenu (Text / Media / Blocks / Layout, collapsible per category, feature-flag gated). Blocks: Rich Text, Custom HTML, URL Link, Image (multi-image), Video, Document, Hero, Carousel, Posts, Campaign, Form, Social, Group, Spacer. Click-outside-to-deselect + Escape close the flyout. Per-block trash icon. Recent-items submenus on Campaign/Form/Posts pre-fill the new block's id.
- **Group block** — recursive composition via `parent_block_id` (migration 026). Flex container with direction, 1-16 columns, item min/max width+height, wrap, align/justify. Each slot is a `group_item` holding ≤1 child; empty slots show an inline picker. Tree assembly via `buildBlockTree(flat)` shared utility.
- **Inline editing** — Rich Text and Custom HTML edit in place on the block preview. HTML block has a code ↔ preview toggle (CodeMirror 6 with HTML lang), drag-resize on the bottom edge, and per-block height persisted in `localStorage` under `sitesurge.editor.blockHeights`.
- **Content templating (`{{ … }}`)** — block text/HTML content is resolved through a template engine (`packages/cms/src/services/template/`: pure tokenizer→parser→expression→evaluator, framework-free + unit-testable; SDK-backed `runtime.ts` resolvers with per-render caching). Supports variables + nested props (`{{post.title}}`) + **array/object index access** (`{{product.media[0].url}}`, literal numeric/string indices; dynamic `[expr]` not supported), entity functions (all accept **id OR slug**: `{{campaign('slug').title}}`, or whole-entity render when no property: `{{form('id')}}` → interactive `FormRenderer`, `{{campaign('slug')}}` → the FULL campaign — image, title, slug, descriptions, raised/goal, donation form — via the shared `CampaignDetail` component reused by the `/campaigns/:slug` page; per-field args `title`/`slug`/`shortDescription`/`fullDescription` each take a **bool** (show/hide) or a **string** (override + show), and `image`/`raised`/`form` bools toggle those sections (`{{campaign('x', title=false, shortDescription='Give today')}}`), `{{campaignLink('slug')}}` → the campaign teaser CARD (`CampaignCard`, shared with the `campaign` content block), posts → cards), `{{if}}/{{else if}}/{{else}}/{{endif}}` + `{{for x as item}}…{{endfor}}` logic, collections (`posts()`), counts (`postCount`), and value utilities (`formatCurrency`/`formatDate`/`truncate`/`default`/…). **Template `formatCurrency(value, showDecimals?, currency?)`** formats a MAJOR-unit amount (`55` → `$55.00`, not cents — distinct from the cents-based `utils/format.formatCurrency` used in app code); always 2 decimals, pass `false` to hide them (`$55`); pairs with the product provider's dollar `variants[].price` (`{{formatCurrency(product.variants[0].price)}}`). Unknown refs / parse errors are ignored (console-warned). Auto-context: a post page exposes `post`, a campaign page `campaign`, a post-embed block its embedded post. Rendered by `components/blocks/TemplatedContent.tsx` (HTML chunks via `display:contents` interleaved with whole-entity components) — content with no `{{ }}` renders identically to the prior `innerHTML` (zero overhead). Editor reference: a collapsible **Variable & Function Reference** at the bottom of the block Edit panel (`TemplateReference.tsx`) + full docs at **`/admin/help/variables-and-functions`** (`/admin/help` index; every entity schema collapsible). Reference data: `services/template/reference.ts`. **Engine location:** the pure tokenizer/parser/evaluator now lives in `@sitesurge/types` (`packages/shared/src/template/`, re-exported from the barrel) so both the client and the SSR resolver share ONE engine; each side supplies its own `TemplateRuntime` (cms `services/template/runtime.ts` via the client SDK; api `services/ssr/templateRuntime.ts` via backend services). **SSR:** post `content` + page block text are template-resolved **server-side** for SEO (`resolveContentForSsr` in `services/ssr/templateRuntime.ts`, wired into `ssr/routes.ts`; whole-entity refs flatten to indexable HTML; SSR context is anonymous so `{{user.*}}` is empty). Remaining gap: block-based post *bodies* aren't SSR-rendered at all yet (pre-existing — `buildPostBody` renders the legacy `content` field, not `post_content_blocks`).
- **Image block** — multi-image with thumbnail strip, per-image Select Media / Upload New / URL paste / alt / caption / link / allowMaximize. Block-level direction + item min/max width+height (any CSS length).
- **Social block** — provider + count + per-slot pinning. Auto-feed when no slots are filled; pinned posts otherwise. Per-slot inline search dropdown of recent posts; "Edit…" opens a full search modal preconfigured to the provider.
- **Carousel block** — items are **media** (image/video slide) or **entities** (`HeroItem.type='media'|'entity'`; legacy `'posts'` still renders but is no longer offered in the add UI). The add-item control is a single minimal dropdown (**Media** → select/upload · **Entities** → add an entity item). An **entity item** holds an `EntityBlockSettings` (entity type + content-block template + binding: current-page / a specific entity / several / a query) — reusing the `entity` block's `EntityBlockEdit` panel — and at render expands into ONE slide per resolved record, each rendered via that template (`{{entity.field}}` bound). Rendering seam: the presentational `HeroCarousel` renders a slide's `contentNode` when present (else the media backdrop + text overlay); `ResolvedHeroCarousel` resolves posts/entity items in an async pass and builds each entity slide's JSX via an **injected** `renderEntitySlide` (`renderEntityTemplateSlide`, exported from `BlockRenderer`) so `ResolvedHeroCarousel` needs no `BlockRenderer` import (no cycle). The injected renderer is the same helper the `entity` block uses per-record (DRY). Same resolver drives the admin preview and the public renderer. **Multi-item paging:** `HeroCarouselOptions.itemsPerPage` (visible items at once, default 1) + `scrollBy` (items advanced per page/swipe, default 1) + `itemGap` (CSS length between items, default 0) + `sidePadding` (labelled **Padding** in the editor; any CSS padding — a SINGLE value insets both sides so the nav arrows sit in the gutter beside the items, MULTIPLE values are a full `padding` on the carousel box e.g. `0 64px 40px` where the BOTTOM value reserves space under the slides for the dots so they don't sit over the cards; `sidePadInline`/`isMultiPad` derive the horizontal component for arrow centering) — the presentational `HeroCarousel` sizes each slide to `calc((100% - (perPage-1)·gap) / perPage)`, steps by `scrollBy` (translate `(100%+gap)/perPage` per item), wraps by page, and renders one dot per page. **Mobile overrides:** `listOnMobile` (render items as a plain vertical list — no track/arrows/dots — on mobile; hides the mobile items-per-page/scroll-by/side-padding options), `itemsPerPageMobile` / `scrollByMobile` / `sidePaddingMobile` / `itemGapMobile` — each falls back to its desktop value when unset. **Mobile detection:** `isMobile = matchMedia('(max-width: 768px)') OR (previewBreakpoint() !== '' && measured container width ≤ 768)` — the second term makes the mobile overrides + list mode also fire in the admin's **mobile PREVIEW** (which caps the container width but not real `@media`), while a genuinely narrow desktop column stays desktop (previewBreakpoint is '' on the public site). Editor has a "Mobile (≤768px)" subsection with the list toggle above the (conditionally-shown) paging options. A `.hero-carousel__viewport` clips the track at the CONTENT box so items don't peek into the side-padding gutters; arrows center in the gutter. `minHeight` prop (from block `style.minHeight`) floors the carousel container so a `height:100%` carousel fills a stretched group slot. **Entity slide fill:** an entity item's template renders as the slide FILLING it — `.hero-carousel__slide--entity` stretches its `.hero-carousel__entity` wrapper (full width+height, `height:100%`), the `.block__inner--contained` site-max-width cap is dropped (full-bleed width), and `.block__inner` becomes the positioning context so the template's own `position:absolute; inset:0` layers AND its block padding land inside the PADDED content box (not escaping to fill the raw slide, which ignored the padding). Only a template whose ROOT block sets a height (`.block--has-height`, e.g. `style.height:100%`) fills the slide vertically; a natural-height card template (e.g. a product card, no height) keeps its content height, vertically centered — so card carousels are unchanged. The height chain runs block → `.block__inner` → `.html-block` (all `height:100%`) so a flex card template (`height:100%` root, image `flex:1;min-height:0`, caption `flex:0 0 auto`) FITS the slide exactly — image flexes, caption stays visible. The slide is `overflow:hidden` (never a per-slide scrollbar); the template's own layout is responsible for fitting. **Legacy posts items:** `HeroPostsConfig` + `PostQueryEditor` still edit/render existing posts items (banner `featuredImage` backdrop + title + meta line + excerpt + tags + "Read More" via `HeroItem.postMeta`; the author-then-dates-above-excerpt/tags-below layout mirrors `PostListRenderer`); new post carousels use an entity item with the built-in `post` type instead. SSR does not emit entity/posts carousel slides (same known gap as the `entity` block). Shared admin controls in `blocks/PostQueryControls.tsx` back both `PostListBlock` and `PostQueryEditor`.
- **Preview mode** — wraps content in the public `<Layout>` so previews render the real site header, footer, navigation, swatches, fonts, and appearance. Pages also wrap in `.dynamic-page.page-wrapper`; posts in `.post-page.page-wrapper`.
- **Posts & pages** — drafts, publish, revisions, SSR body for SEO, RSS at `/feed.xml`, full-text search.
- **Campaigns + donations** — Stripe Elements, recurring subscriptions, public-donor toggle.
- **Forms / surveys / polls** — typed question library, submission inbox, CSV export. A form's **on-submit action** is `submit` (save only), `subscribe`, or `email`; `subscribe`/`email` do NOT save unless `actionConfig.saveSubmission` is true (a common surprise — "Submit a Tip" emails without keeping a copy). `actionConfig.emailTo` takes a comma/semicolon-separated list and sends ONE message per recipient (no shared To: header, one bad address can't sink the rest); subject/body are `{{ }}`-templated on keys slugified from the question labels (`Your tip` → `{{your_tip}}`).
- **Contact page** — `/contact` is an ordinary **CMS page** (slug `contact`) rendered by `DynamicPage`, NOT a hardcoded component. Its form is the `contact` **Form** entity embedded via a `form` block, so submissions land in the Forms inbox and the recipients are edited in the admin. Previously it was a static `pages/Contact.tsx` posting to `POST /messages` (the `contact_messages` table), whose notification address came from the **`ADMIN_EMAILS` env var** — invisible in Settings, which made "who gets contact email?" unanswerable from the admin. That component and the hardcoded `/contact` branch in `ssr/routes.ts` are gone; SEO now comes from the page row + its blocks. The `messages` module still exists and is still wired to `ADMIN_EMAILS` for any other caller.
- **Users & roles** — email/password + Patreon OAuth, member tiers, gated content, user/IP bans. Roles: `anonymous | member | editor | admin | sysadmin`. **`editor`** = content-editing staff: signs into the admin (limited nav — no Plugins/Settings/Users/Mailing Lists/Shop), edits content (posts/pages/media/campaigns/forms/messages via the `staff` auth tier), and can be attributed as a post author. Predicates `isAdminRole` (admin/sysadmin) + `isStaffRole` (+editor) in `@sitesurge/types`. Post author = `authorId` (a staff user) with `author` (displayName) derived; the Post editor's Author dropdown reads `GET /users/authors` (staff-tier, minimal fields); new posts default the author to the creator. **Email verification** — an admin-only **Users settings page** (`/admin/users/settings`, linked from the Users header; `users_settings` keyed row) toggles "Require new users to validate their email before login" (default ON) + an optional block-editor-authored verification email (empty → built-in default). Self-registered **members** (only) get `email_verified=false` + a token and a `/verify?token=` email; `authenticateWithEmail` blocks unverified members; `POST /auth/verify-email` confirms + auto-logins. Migration 077 adds `users.email_verified`/`verification_token`/`verified_at` (`DEFAULT true` grandfathers all existing/staff/Patreon accounts). Staff + Patreon accounts are never gated.
- **Admin Channel (live staff presence)** — a staff-only WebSocket at **`/ws/admin`** (attached to the main HTTP server in `lib.ts`; upgrade authed from the `accessToken` cookie JWT, rejected for non-staff) broadcasting who's in the admin, what page they're on, and active/idle status — to avoid concurrent-edit conflicts. Backend `services/adminChannel/` (`server.ts` WS + heartbeat + idle sweep; `registry.ts` in-memory presence aggregated per-user; `config.ts` idle timeout). Protocol: client sends `hello`/`navigate`/`active`/`inactive`/`list`/`ping`; server replies `welcome` (self + `activeTimeoutMs`) then fans out `presence` (full roster) on every change. REST fallback `GET /admin-channel/presence` (`cms.adminChannel.presence`). Client singleton `services/adminChannel.ts` (auto-reconnect; reports activity from an idle timer + tab-visibility + window-focus listeners so switching tabs/windows or going idle flips to inactive and returning flips back; fans navigation). UI: `components/admin/presence/AdminPresence.tsx` in the sidebar footer (above `.admin-layout__user`) — collapsed shows "N users connected", clicks expand UPWARD into a list (name + role + active/idle dot + short "10s ago" + current page; self labelled "(you)"), header has an `×` to collapse. `SamePageWarning.tsx` shows a dismissible corner banner when another *active* staff user is on the SAME admin page. Idle timeout is operator-configurable in **Settings → General** ("Admin presence idle timeout (seconds)", default 60; `admin_channel` keyed setting → `activeTimeoutSeconds`, delivered to clients in the `welcome` message). **nginx must pass WebSocket upgrade headers** for `/ws/admin` (see `deploy/nginx-surge.conf`: `map $http_upgrade $connection_upgrade` + `proxy_set_header Upgrade/Connection`). In-process/single-node presence (a multi-instance deploy would need Redis pub/sub — deferred).
- **Contacts (CRM)** — opt-in feature module (`contacts`, requires `users`). A `contact` **core entity type** (Entities system) adopting the migration-created `ce_contact` table (migration 090; fields `userId, firstName, lastName, email, mobilePhone, primaryPhone, streetAddress1/2, city, zip, state, country, timeZone` — name/email/phones searchable via per-field ILIKE; `userId` links a registered user, NULL until matched). Enabling seeds the type (`onEnable` scaffolds it; a post-commit `seedCoreEntityTypes()` reload makes it live without a restart — also fixes the shop→product papercut). Admin **Contacts** sidebar item under Users → `/admin/entities/contact/data` (the entity Data table: sortable/searchable/paginated + New/Edit/Copy). PII guard: `contact`/`user` are a `PRIVATE_TYPES` denylist in `services/entities.ts` — non-staff generic reads 404 (other internal types stay publicly renderable). **Registration match/link:** `services/contacts.ts` + feature-gated `routes/contacts.ts` — `GET /contacts/me` (linked contact, profile prefill), `GET /contacts/me/match` (UNLINKED contact by the caller's email), `POST /contacts/me/link` (`{contactId, fields?, importProfile?}`). On first authenticated load a **member** with an unlinked email match sees `ContactMatchModal` (public `Layout`, driven by the auth store's `contactPrompt`; staff excluded) to review/edit + import (copies name/city/state onto the profile) or dismiss — **either action links the contact** (`userId` set) so it's never offered again. **Profile augmentation:** the `/profile` page shows contact fields (phones/address/zip/country/timezone) when enabled; `PUT /auth/me` writes base user columns and upserts the linked contact row (`contactsService.upsertForUser`) with all fields (redundant name/city/state included). SDK `cms.contacts.*`. Import: `pdfplumber` line-table parse of a Groundhogg export → `ce_contact` (deduped by email, `No`=empty, `userId` NULL).
- **Mailing lists** — opt-in feature module (`mailing_lists`, requires `users`). Per-list subscribers (registered users or email-only), token-based one-click `/u/:token` unsubscribe + RFC 8058 `List-Unsubscribe` headers, optional per-list double opt-in. Mail templates reuse the existing block editor; backend email renderer adapts every block type to table-based inline-style HTML and resolves `swatch:{id}` refs to literal hex via the palette. Send wizard creates tracked jobs (`mail_send_jobs` + `mail_send_recipients`) processed by an in-process worker with concurrency/delay knobs and a boot-time resumer. **Bulk reliability (5k+):** the worker claims recipients atomically (`claimBatch` — `pending → 'sending'` under `FOR UPDATE SKIP LOCKED`, migration 078) so overlapping runs never double-send; `'sent'` is terminal (never re-pulled → no duplicate to an already-sent address); a crash requeues stranded `'sending'` rows on resume; `resumeRunningJobs` resumes both `running` and `pending` jobs on boot; `sendWithRetry` adds exponential backoff for transient SMTP blips; the SMTP transport is pooled with connection/socket timeouts. Provider abstraction (`MailProvider`): SMTP (Nodemailer, default — works with any SMTP relay incl. SendGrid/Mailgun/Postmark/AWS SES / Mail Manager) and stubs for native REST adapters. **Template engine:** the mail render pass resolves `{{ }}` through the SAME full engine as content/SSR (`services/mail/templateRuntime.ts` → `resolveMailTemplate`, wired into the send worker + preview) — every text field of every block (incl. hero `content`, url-link `title`/`description`) plus subject + preheader support the full grammar (functions, `if`/`for`, entity refs) and the complete variable set. Welcome / donation-receipt / **email-verification** emails flow through the shared transactional service (`services/mail/transactional.ts` → `renderStandaloneMail`/`sendTemplatedEmail`).
- **Shop / ecommerce** — opt-in feature module (`shop`, requires `users`). Catalog: products with ≤3 options → auto-generated variants (per-variant price/inventory/SKU), multi-image+video media with sort + main-image, hierarchical categories, curated collections, normalized tags. Reviews with admin moderation + rating denormalization (`rating_avg`/`rating_count`). On-site Stripe checkout (PaymentIntent + Elements + Stripe Tax) with guest checkout + client-side cart; server re-validates every line item's price/inventory. Orders with fulfillment/tracking/refund/receipt + digital-download tokens. Shop settings = config + storefront appearance (two `site_settings` rows). Admin `/admin/shop/*`, storefront `/shop/*`, SDK `cms.shop.*`, all 404/hidden when the `shop` feature is off. All tables `-- @feature shop` (migrations 039–049).
  - **Dynamic shipping (Printify) + method selection** — Printify products' base prices EXCLUDE shipping; the checkout fetches live rates from `POST /v1/shops/{id}/orders/shipping.json` (`printify/client.calcShipping`; **cents**; V1 is the only order-shipping endpoint — no V2 equivalent). `getPrintifyShippingOptions` returns ALL methods (`economy`/`standard`/`priority`/`express`/`printify_express`) and — unlike the old silent-$0 `calcPrintifyShipping` — **surfaces failures**: an API error logs with context (`Printify shipping calc failed`) and returns `ok:false`, so `checkout.buildShipping` falls back to the shop's configured **flat rate** (`settings.shipping.flatCents`, default **$8.99**) and flags `shippingQuoteFailed` (storefront shows a note) instead of shipping free. `previewCheckout`/`createCheckout` accept `shippingMethod`; the preview returns `shippingOptions[]` (id/label/cents = native flat + provider method) + the picked method; the storefront `ShopCheckout` renders a radio selector (re-previews on change) and passes the choice to `create`. The selected method label persists on the order (`shop_orders.shipping_method`, migration 088) and shows in the admin order detail, storefront confirmation, and buyer/seller emails ("Shipping (Standard)"). **Catalog hygiene:** a full Printify sync reconciles the catalog — products whose Printify id no longer exists (dead/duplicate rows) are archived (`archiveExternalProducts`), so carts only contain quotable products (a bad/stale variant id → Printify 404 → the fallback, not a crash). **Stable variant UUIDs:** the product-structure writer (`shopProducts.repo`) UPSERTS variants keyed on `external_id` (updates in place) instead of delete+reinsert, so a resync no longer regenerates variant ids — carts/order refs survive syncs. `previewCheckout` is LENIENT (a removed/stale variant is reported in `unavailableVariantIds`, not thrown), so the storefront prunes those lines + notifies; `createCheckout` stays strict.
  - **Two-step checkout:** the storefront `ShopCheckout` is a **Continue → Confirm** flow. Step 1 (details): the CTA is **Continue** ("you won't be charged yet"); on submit it validates the form + tokenizes the card (`stripe.createPaymentMethod` → brand/last4 for the review) and locks in the shipping quote. Step 2 (confirm): the input form is hidden (kept mounted so the Stripe card iframe persists) and a read-only review shows contact / shipping+billing address / card "ending in ####" / items / shipping / total; the CTA becomes **Place Order** (an **Edit details** link returns to step 1). The order summary now lists the cart line items (image / name / qty / price).
- **Events & calendar** — opt-in feature module (`events`). Events with recurrence, per-date overrides, attendee registration and tiered ticketing. **Recurrence:** a rule (`daily|weekly|biweekly|monthly[:dayOfMonth]|yearly`, NOT iCal) + `recurrenceUntil`, expanded at READ time by the pure engine in `@sitesurge/types` (`utils/recurrence.ts`) — no occurrence rows are stored. Per-date `event_occurrence_overrides` cancel or retitle one date of a series (admin sees a cancelled date flagged; the public never sees it). Month-grid geometry is shared by the server and the SPA via `@sitesurge/types` (`utils/calendarGrid.ts`) so the two can't disagree about which window a month covers. **Slugs:** auto-derived from the title and de-duplicated server-side — the first collision becomes `-1`, then `-2` (`events.slug` is UNIQUE, so this is what stops a second "Summer Gala" being a 500); a write that loses the probe→insert race retries. When the stored slug differs from the one submitted, the admin modal STAYS OPEN, shows the corrected value with an amber notice, and moves to the event's `/admin/events/:id` URL. That notice rides in the router's location **state**, because `/events/new` and `/events/:id` are separate `<Route>` entries sharing one component — crossing between them remounts it and would wipe a signal. **Descriptions are Markdown** (`renderMarkdown`/`stripMarkdown` in `@sitesurge/types`, `utils/markdown.ts` — a small dependency-free renderer that ESCAPES first and emits only its own tags, so its output is safe to `innerHTML` without a sanitiser; link protocols are allow-listed). The detail page renders it into `.rich-text`; `<meta name=description>` and the calendar's brief list use the stripped plain text (a `<button>` can't hold block HTML). **Registration:** an attendee row per (event, occurrence date) — distinct from *subscribing*, which only signs up for notifications. `registrationFields` ALWAYS includes `email`, normalised server-side (`normalizeRegistrationFields`), so a direct `PUT` can't produce a form that collects no address yet still requires one. **Ticketing** (requires `shop`): tiers with optional per-occurrence caps; the cart is virtual (`kind: 'event_ticket'`) and **re-priced from the database** on checkout — a tampered price or quantity changes nothing. Free tickets confirm immediately with codes; paid tickets return `payment_required` for the Stripe step and consume no inventory until payment succeeds. **Notifications:** publish announcements + a reminder sweep over email and Web Push (VAPID; `web-push` is an OPTIONAL dependency — without it the module runs email-only), idempotent via an `event_notifications_sent` claim ledger. **Service layout:** `services/events.ts` is a BARREL over `services/events/` split by responsibility — `settings` / `crud` / `calendar` / `occurrences` / `subscriptions` / `notifications` / `registration` / `tiers` / `tickets` / `purchase`. Dependencies run one way (`crud → notifications → settings`, `subscriptions → crud`), which is why signing up and sending out are separate modules. Admin `/admin/events` (calendar + URL-routed modal, `/admin/events/new`, `/admin/events/:id`) and `/admin/events/settings`; public calendar at the configurable `eventsUrl` (default `/events`, validated against reserved paths and existing page slugs) + `/events/:slug`. Content block `event` + template function `{{event('slug')}}`. Known gap: the paid-ticket Stripe card step returns `payment_required` but the card flow is not yet wired.
- **Order receipts (PDF)** — `GET /shop/orders/:orderNumber/receipt` (`raw`, `optional` auth, same order-number reachability as the confirmation view) streams a generated PDF; `services/shop/receipt.ts` renders it with **PDFKit** (imported lazily so its font metrics stay off boot for installs that never sell). Rendered on demand, never stored, so it always matches the order's current status/tracking. SDK `cms.shop.orders.receiptUrl(orderNumber)` returns a URL rather than bytes — the endpoint sets `Content-Disposition: attachment`, so browser navigation gives a proper save-as with the right filename. Note the anonymous projection of an order omits addresses, so a receipt downloaded without admin auth carries no ship-to block (deliberate: an order number alone must not reveal a customer's address). The storefront confirmation page puts the button at the top right, across from the order/status row, and **polls the order every 4s (cache-bypassed, 2-minute cap) while the status is unsettled** — Stripe confirms out of band, so a just-paid order can read `pending` until the webhook lands, which previously looked like a failed payment until the buyer refreshed.

## Permissions (required for new features)

**Any new feature module — or any addition to an existing one — must check that a permission exists for each read or write action that should be gated.** If the feature has no suitable permission, add one rather than falling back to a role check.

- Declare it in `packages/api/src/services/permissions/catalog.ts`: `CORE_PERMISSIONS` for always-on behaviour, or `FEATURE_PERMISSIONS[<featureKey>]` so it registers only when that feature is enabled. Boot registers the catalog for enabled features, so a newly enabled feature's permissions appear in the admin without a restart.
- Check it with the manager, never with a hand-rolled role comparison: `can(subject, key)`, `requirePermission(subject, key)` (throws 403), `check()` (returns the deciding reason), `permissionsFor(subject)`. Import from `services/permissions`.
- Key format is `feature:action` (`posts:write`, `shop.orders:refund`). Pick defaults that PRESERVE today's behaviour — a permission that silently removes access from existing users is a regression, not a feature. Tightening is the operator's decision, made in Settings → Permissions.
- Precedence is fixed: sysadmin → user grant → role grant → the permission's own default. An unknown key DENIES, so a typo fails closed.
- Permissions layer ON TOP of the route auth tier; they do not replace it. Keep the tier (`staff`/`admin`/…) and narrow within it.

Full model: `docs/sdk/permissions.md`; in-admin reference at `/admin/help/sdk/permissions`.

## Admin styles

- **Forms: ALWAYS use the `FormField` component** (`components/admin/forms`) for admin form fields — never a raw `<label>`+`<input>`. It renders the ONE canonical field label used across the whole admin: **uppercase, bold, small, letter-spaced, muted** (`.admin-form-field__label` in `forms.scss`; broadened to `.form-group > label` / `.block-edit-form__field > span` / `.block-style-editor__label` so legacy markup matches). `FormField` self-imports its scss (styled even when imported directly). Supports `tooltip` (inline help) + `hint` (sub-text). Do NOT generate forms with unstyled labels.
- **Edit/list page headers are sticky by default** — use `<div class="admin-header">` (title + `.admin-header__actions` for Save/manage); `.admin-header` is `position: sticky; top: 0` globally.
- `packages/cms/src/pages/admin/AdminLayout.scss` is a slim index — actual rules live in `packages/cms/src/pages/admin/styles/_*.scss` partials grouped by feature (admin shell, block editor, inline editors, dashboard, settings, etc.) and in `packages/cms/src/styles/shared/` for things both the admin and the main site use.
- **Read `packages/cms/src/components/admin/ADMIN_STYLES.md` before adding admin styles.** It documents which partial owns what, when to hoist to `styles/shared/` vs keep admin-local, and the convention for `@use 'sass:color';` + `@use '../../../styles/variables' as *;` at the top of each partial.
- Repeated inline `style={{ ... }}` patterns belong in a partial. Common shared helpers (`.confirm-modal*`, `.preview-empty-message`, `.form-help-muted`) live in `styles/shared/` or `global.scss`.
- **Content-block preview containment** — `.content-block__preview-body` is `position: relative` (the positioning context for a block's inner content) so a block whose markup uses `position:absolute; inset:0` (e.g. a full-bleed custom-HTML block) resolves against the body — which sits BELOW the header bar — instead of the whole `.content-block`, where it would paint up over the `.content-block__hover-bar` header and steal its clicks. The body is intentionally NOT clipped (`overflow` stays visible) — `position: relative` alone prevents the over-header paint, while clipping would hide legitimate content that overflows a block's fixed height (e.g. a card whose text sits below a full-height image); the editor now matches the un-clipped public render.
- **Custom-HTML inline-editor preview** — the `HtmlInlineEditor` **Preview** tab renders through `TemplatedContent` with the SAME `entities` bag the deselected preview uses (`templatePreviewContext()` — the template editor's sample record; empty on page/post editors). Without it, `{{entity.field}}` resolved to empty and the Preview rendered blank.
- **Full-bleed admin pages** — the admin content column caps each page root at `--admin-content-max-width` via `> *:not(.admin-full-bleed)`; a page opts into full width by adding `admin-full-bleed` to its root (Page/Post editors and the **entity template editor** `TemplateEditor` do this).

### Key Patterns
- Snake_case in DB, camelCase in API responses (mapped in repositories/services via `mapRow`)
- Redis caching on public endpoints with pattern-based invalidation
- Multer for file uploads, sharp for image thumbnails, nanoid for filenames
- Custom error classes (AppError, NotFoundError, ValidationError, etc.)
- PostgreSQL triggers for: updated_at, campaign totals, form submission counts, search vectors
- **Route manifest framework** — `defineRoute({ method, path, auth, summary, input(zod), handler })` + `registerModule()` in `packages/api/src/api/`. Auth tiers: `public | optional | user | staff | admin | apiKey`; `staff` = admin/sysadmin/editor JWT (content modules) — `admin` and `apiKey`-tier routes accept an admin JWT **or** a scoped `ssk_` API key (API keys satisfy `staff` too) (`Authorization: Bearer ssk_…`; GET/HEAD→`read+`, mutations→`write+`, hierarchy `read < write < admin`); `optional`-tier routes also accept keys (valid key = machine client, gets admin-shaped response; invalid key fails with 401). Keys cannot manage keys (`/api-keys` rejects key auth with 403). Key writes audit as `api-key:<name>`. Admin-shaped responses bypass the public Redis cache. Handlers return data or `reply(data, {meta, status})`; errors throw → `middleware/error.ts`. `manifest()` emits the machine-readable route list. Bearer-authenticated requests skip CSRF. **Sweep complete: all 28 route modules are on the manifest** — the legacy `handleRouteError`/`send*`/`handleBulkAction` helpers and `utils/response.ts` are deleted.
- **Services own business logic** — `services/<module>.ts` is the canonical home; `routes/` are thin manifests (no inline SQL, no `res.json`, no try/catch); SQL lives in `repositories/` and `services/`; `sdk/` re-exports from `services/` (`cms.*` still works).
- **API docs generated from the manifest** — `npm run docs:api` builds the running-mode app, reads `manifest()`, and writes `docs/API.md` + `docs/api-manifest.json` (do not hand-edit those two).
- **Unified list endpoints** — converted modules drop `/public` suffixes: one `GET /<module>` with `optional` auth, role-shaped (anon → published only; admins passing `status`/`sort` get the all-statuses view). Gated content returns `error.code 'CONTENT_LOCKED'` with a preview in `error.details` (`ContentLockedDetails`). First instance: posts (`/posts/public` is gone).
- **Shared request/response DTOs** — every module's wire types live in `@sitesurge/types` at `packages/shared/src/api/routes/<module>.ts` (all 29 modules covered; conventions documented in the barrel header `packages/shared/src/api/index.ts` — module-prefixed names, list responses = element arrays with pagination on `meta`, entity types referenced never duplicated). The backend **binds** its zod schemas to these: `input` schemas use `satisfies z.ZodType<XBody>` where clean, else an `AssertCompatible<z.infer<typeof schema>, XQuery>` compile-time assertion (for query schemas whose coercion makes input ≠ output). **DTO drift is a compile error.** Clients and the backend share ONE definition per shape.

### API Client
- **`@sitesurge/client` is the one networking path.** `services/api.ts` is DELETED — there is no envelope wrapper, no `fetch*` helpers, no `ApiService` class. Every backend call goes through the typed client singleton.
- `services/cmsClient.ts` exports `cms` — `createClient({ baseUrl: window.location.origin, auth: { mode: 'cookie' }, cache: { adapter: 'localstorage' } })`. Cookie mode preserves the httpOnly + CSRF session (no backend change). `cms.onError(...)` is the cross-cutting bus: a non-auth `UnauthorizedError` → session-expired handler; `ServiceUnavailableError`/`NEEDS_SETUP` → redirect to `/setup`. Auth-path 401s are filtered so login failures don't trip the session-expired modal.
- Call sites use `cms.<module>.<method>()` with `try/catch`. Errors are typed (`UnauthorizedError`, `ContentLockedError`, `ServiceUnavailableError`, …). Paginated list methods return `{ data, meta }` (`PageMeta = { page, limit, total, totalPages }`); single-entity GETs return the entity directly.
- Hooks take typed fetchers: `usePaginatedList({ fetch: (params) => cms.<module>.list(params), initialLimit?, params? })`; `useBulkActions({ entityType })` maps to `cms[entity].bulk({ ids, action, value })`. All entity `BulkBody` DTOs agree on `{ ids, action, value }`.
- **Deferred (still on inline `fetch`):** Join's `POST /auth/register` and UrlLinkBlock's `GET /utils/url-preview` remain raw `fetch` calls — known follow-ups to fold into `cms.*` once those routes are exposed on the client.

## Gotchas
- **Config stubs:** each package's root `tsconfig.json` is a one-line `extends` shim pointing at `config/<pkg>/tsconfig.json`. The real config (incl. vite/vitest) lives in `config/`; vite/vitest are invoked with `--config config/<pkg>/...` flags (those set `root`/`envDir` back to the package). Edit the file in `config/`, not the stub.
- **.env exception:** `.env` / `.env.example` stay at `packages/api/` (dotenv default path), NOT in `./config`. Other documented exceptions kept at root: `.editorconfig`, `.dockerignore`, `pnpm-workspace.yaml` + lockfiles, `.github/`, `packages/cms/index.html`.
- **Import scope:** the workspace scope is `@rw/cms-*` (was `@rw/shared`). Import shared types/DTOs/utils from `@sitesurge/types`. `@sitesurge/types` imports from no sibling package.
- **dprint pre-existing drift:** ~250 files predate the formatter config, so `npm run format:check` currently FAILS (known/expected). Don't bulk-reformat as a side effect; format only files you touch.
- **DTO convention + drift:** request/response DTOs for all 29 modules live in `packages/shared/src/api/routes/` — conventions in the barrel header (`packages/shared/src/api/index.ts`). Backend zod binds to them (`satisfies z.ZodType<X>` / `AssertCompatible`), so a DTO mismatch is a compile error.
- **Cache-key contract:** every Redis key string lives once in `CACHE_KEYS` in `packages/api/src/services/cache.ts`; services import a builder for get/set and call a named `invalidateXCache()` for invalidation. NEVER call `cache.del`/`cache.delPattern` from a service — a guard test (`services/cache-contract.test.ts`) fails the build if a raw call appears outside `cache.ts`. Changing a `CACHE_KEYS` string changes a production key.
- **cms-client — IMPLEMENTED:** `packages/cms-client` (`@sitesurge/client`) is fully built: 27 module namespaces, all 234 API routes covered, SWR cache, token auto-load, typed error bus, SolidJS adapter. See `packages/cms-client/docs/Overview.md`.
  - **Doctrine (realized):** All client-side requests route through `@sitesurge/client` (`createClient`). It exposes `cms.<module>.<method>()` for all routes, with SWR caching, token auto-load, and a typed error bus. **`@sitesurge/admin` is fully migrated** — `services/api.ts` is deleted and the `cms` singleton (`packages/cms/src/services/cmsClient.ts`, cookie mode) is the sole networking path. (`POST /auth/register` and `GET /utils/url-preview` now exist and are exposed as `cms.auth.register` / `cms.utils.urlPreview`.)
  - Usage: `const cms = createClient({ baseUrl: 'https://cms.example.com', auth: { apiKey: 'ssk_…' } }); const posts = await cms.posts.list();`
  - `npm run check:drift -w packages/cms-client` — guards client↔API coverage against `docs/api-manifest.json`.
  - `npm run test:integration -w packages/cms-client` — manual live-API smoke test (requires `SMOKE_API_KEY` env + running server).
- **cms-mcp — IMPLEMENTED:** `packages/cms-mcp` (`@sitesurge/mcp`) is an MCP server (stdio) wrapping `@sitesurge/client` in apiKey mode, exposing the whole authoring surface (pages/posts/blocks/every block type/block styles/appearance/swatches/fonts/header/footer/settings/features/media/nav/reference) as **66 tools** so an AI agent can build a site. Config via env (`CMS_BASE_URL`, `CMS_API_KEY`, `CMS_MCP_READONLY`). Adds the block-type catalog (`describe_block_types`), group-nesting + single-post-block ergonomics, and media-from-path/URL. Full reference: `docs/MCP.md`. Design + deficiency audit: `docs/superpowers/specs/2026-07-09-cms-mcp-server-design.md`, `docs/mcp-sdk-deficiencies.md`.

## Important Notes
